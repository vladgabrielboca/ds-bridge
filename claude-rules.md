# Delegation to DeepSeek (ds-bridge): opt-in per chat

**Default: Claude works directly** (edits, builds, tests) in every chat. Delegation to DeepSeek via `ds` (OpenCode agent `worker`) is on only when the user turns it on for that chat: `/delegate`, or the user says "delegate to deepseek" / "use ds" -> run `ds delegate on`. `/delegate off` / "stop delegating" -> `ds delegate off`. While it's on, a hook reminds every turn and the guard blocks direct edits; Claude keeps only planning, architecture, troubleshooting/debugging, orchestration and review, and these rules apply:
- Execution = writing/editing code or files, refactors, mechanical edits, writing tests, running builds/tests to complete a change. Delegate everything bigger than a small edit; small edits (up to 20 changed lines, 2 edits per file per turn) Claude makes directly, since a brief + review costs more. No edits through Bash heredocs/sed.
- Brief: `ds run -C <project> -` with the brief on stdin, written per the planner playbook (printed once by `ds delegate on`, again after compaction; `ds playbook` to reread): sections GOAL / CONTEXT / FILES / STEPS (numbered, one exact action each) / DO NOT / DONE WHEN, every decision already made, project rules copied in verbatim (the worker sees no skills or memories). `ds run` refuses briefs that miss sections or use vague words; fix the brief, don't work around the lint. Don't paste file contents; the worker reads them itself.
- Learning the code: don't open source files to plan; ask `ds research -C <project> "<question>"` (read-only, ≤200 words + refs with verbatim anchor lines) and plan from that. Open a file only if it says UNSURE or low confidence.
- Review only what ds prints. A passed `--check` is trusted: ds shows the diff stat only (full: `ds diff JOB`), so make DONE WHEN a real test of the step. Without a check you get the capped diff. Don't re-read the changed files.
- The worker can see images: for visible output (UI, plot, render, page) put a LOOK step in the brief and read its VISUAL line instead of opening the images yourself; open one only to confirm a flagged problem or for a required final sign-off. Attach reference images with `-f` (also on `ds revise`).
- Prefer `--check "<test cmd>"` so the bridge runs the acceptance check itself and the worker auto-fixes failures before you see the result; trust the check section over the worker's CHECKS line.
- Independent subtasks can run in parallel: start several `ds run ... --paths <their files>` with run_in_background, then review each report as it arrives. Jobs on overlapping paths are refused.
- Start every `ds run` / `ds revise` as a tracked background task (the Bash tool's run_in_background), never with a shell `&`: an untracked job's completion never reaches Claude, so its result sits unread.
- First job in a project without AGENTS.md: run `ds init -C <project>` and review it like any other job.
- Then exactly one of: `ds approve JOB`, `ds revise JOB "<numbered points>"` (same session; output shows only that round's diff), or `ds reject JOB` (restores the pre-job snapshot).
- When a job is not finished (check FAIL, BLOCKED, errors, repro FAILED/WEAK), ask the user one question: a Sonnet subagent finishes it (Agent tool with model sonnet, given the brief, the `found:` note and the job's dir), `ds revise` with the findings, or stop. Don't take it over yourself with Opus; don't pick for the user.
- Bug fixes: `ds run --fix` makes the worker write a reproduction test first; ds checks it fails on the old code and passes on the new (`--- repro: fail→pass verified`).
- Parallel jobs (`--paths`) run in private copy-on-write copies; `ds approve` lands the changes (3-way, under a lock). On CONFLICT: `ds rebase JOB`, then `ds revise` to resolve the markers.
- If ds errors (quota, region, auth, timeout), tell the user and stop; don't silently do the work yourself.
